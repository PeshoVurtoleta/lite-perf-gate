lite-perf-gate 1.0.0 -- the shape of a leak

A two-point scaling probe: measure at N and k·N iterations, count minor GCs (scavenges), and verdict. A zero-alloc hot path stays flat at both; an allocating one shows scavenges scaling with total bytes. The detector self-validates each run via positive/negative controls -- if either misbehaves, the gate refuses to judge. Traces below simulate the physics -- real perf-gate runs under Node with --expose-gc --max-semi-space-size=4.

    A silent false pass is the failure mode gate tooling has to eliminate. perf-gate requires the positive control to force more than maxScavenges + 3 scavenges (proof the detector sees allocation) and the negative control to stay at or below maxScavenges (proof the runtime flags are right). If either fails, no scenario is judged; you get an explicit "detector broken" instead of a spurious PASS.

    Tuning knobs what your V8 flags do

    Why --max-semi-space-size=4 sharpen the probe

    V8's default young generation is 16 MB. At 200k iterations of 64-byte objects, you produce ~12 MB -- possibly fitting without a single scavenge. Shrinking to 4 MB forces scavenges on smaller cumulative allocation and sharpens sensitivity. Drag the semi-space slider left and watch the positive-control trace steepen; the negative stays flat.

    Scavenges and retained heap look fine for a pooled builder that grows rarely. But engine internals -- poolGrowths, totalAllocations, node births -- carry information the two heap signals don't. statsOf deltas are checked against thresholds the same way; a failure names the counter, not just "the gate tripped".

    Threshold config what the suite would set

    A common shape: { poolGrowths: 0 }. A well-tuned pool allocates once at setup(); any growth during the measurement window means the initial size was wrong.
